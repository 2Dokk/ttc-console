# 설계 문서 — 위성 지상국 관제 콘솔 (TT&C Console)

시스템 요구사항에서 출발해 소프트웨어를 어떤 단위(CSCI)로 나눴는지, 그리고 각 요구사항이 어느 코드에서 구현되고 어떤 시험으로 확인되는지를 정리한 문서입니다.

> **이 문서에 대해 미리 밝혀 둡니다.**
> 이 프로젝트는 기능을 먼저 구현한 뒤, 현업 피드백을 받아 **요구사항과 구조를 역으로 정리**했습니다.
> 실제 사업에서는 반대 순서(요구사항 → 설계 → 구현)로 진행합니다.
> 문서 형식은 방산 소프트웨어 문서 체계(MIL-STD-498 등)를 **참고**했을 뿐, 표준을 준수한 산출물은 아닙니다.

---

## 1. 시스템 개요

저궤도 위성은 지상국 상공을 지나는 수 분 동안(패스)만 교신할 수 있습니다. 이 시스템은 그 제약 아래에서
위성의 상태를 감시하고 명령을 보내는 지상국 관제 시스템입니다.

**운용 개념**

1. 지상국은 궤도 정보(TLE)로 다음 교신 가능 구간(AOS~LOS)을 예측한다.
2. 운용자는 교신 여부와 무관하게 명령을 등록한다. 교신 불가 중에는 지상에서 대기한다.
3. 교신이 시작되면 대기 중인 명령을 순서대로 전송하고, 위성 상태 데이터를 실시간으로 받는다.
4. 교신 불가 중 위성이 저장해 둔 상태 데이터는 다음 교신 때 내려받아 이력을 채운다.

**범위 밖 (이 프로젝트에서 다루지 않음)**

- 관측 임무 데이터(EO/IR·SAR 영상)의 X 밴드 대용량 다운링크와 그 전송 계획
- 위성 여러 대, 지상국 여러 곳의 안테나 자원 배분
- 실제 안테나·송수신 장비 제어

## 2. 시스템 요구사항 (SYS)

| ID | 요구사항 | 비고 |
|---|---|---|
| SYS-01 | 지상국은 대상 위성의 교신 가능 구간(AOS/LOS)을 사전에 예측해야 한다. | 공개 궤도 데이터(TLE) 기반 |
| SYS-02 | 시스템은 현재 교신 가능 여부를 운용자에게 실시간으로 표시해야 한다. | |
| SYS-03 | 원격명령은 교신 가능 구간에서만 송신해야 한다. | |
| SYS-04 | 교신 불가 중에 등록된 명령은 유실 없이 보관했다가 다음 교신에서 송신해야 한다. | |
| SYS-05 | 원격명령은 운용자가 등록한 순서대로, 중복 없이 위성에서 실행되어야 한다. | 전송 중 유실이 있어도 보장 |
| SYS-06 | 시스템은 명령의 **위성 도달 여부**와 **실행 결과**를 구분해 운용자에게 제공해야 한다. | |
| SYS-07 | 운용자는 아직 송신되지 않은 명령을 취소할 수 있어야 하며, 유효 기한이 지난 명령은 송신하지 않아야 한다. | |
| SYS-08 | 교신 가능 구간의 위성 상태 데이터는 실시간으로 수신·저장해야 하며, 수신 누락을 식별할 수 있어야 한다. | |
| SYS-09 | 교신 불가 구간의 위성 상태 데이터는 다음 교신에서 확보해 이력의 공백을 채워야 한다. | 위성 온보드 저장 활용 |
| SYS-10 | 위성 상태가 정해진 한계치를 벗어나면 운용자에게 경보해야 한다. | 고정 한계치 비교 |
| SYS-11 | 시스템은 실제 위성 없이 시험·시연할 수 있어야 하며, 시험 수단은 운용 소프트웨어와 분리되어야 한다. | 시뮬레이터, 시간 가속 |
| SYS-12 | 소프트웨어 재시작 후에도 명령 상태와 상태 데이터 이력의 일관성이 유지되어야 한다. | |
| SYS-13 | 전송 중 손상된 프레임은 수신 측이 검출해 폐기해야 하며, 손상된 내용이 운용에 반영되어서는 안 된다. | 업링크·다운링크 양방향 |
| SYS-14 | 응답 없는 재전송이 한도를 넘으면 송신을 중지하고 운용자에게 알려야 한다. | 링크 장애를 조용히 숨기지 않음 |

## 3. 소프트웨어 구조 (CSCI 분할)

### 3.1 분할 결과와 이유

| CSCI | 이름 | 맡는 요구사항 | 이렇게 나눈 이유 |
|---|---|---|---|
| **CSCI-1** | 지상 관제 소프트웨어 | SYS-01~10, 12 | 운용 형상의 핵심. 변경 시 검증 부담이 가장 크므로 가장 엄격히 관리한다. |
| **CSCI-2** | 운용자 콘솔 소프트웨어 | SYS-02, 06, 10 (표시 측면) | 실행 환경(브라우저)과 언어가 다르고, 화면 요구는 운용 중 자주 바뀐다. 표시 변경이 관제 로직의 재검증을 유발하지 않도록 분리한다. |
| **CSCI-3** | 위성·링크 시뮬레이터 | SYS-11 | **시험 수단이므로 운용 형상에 포함되면 안 된다.** 실제 위성·지상 장비로 교체될 자리이기도 하다. |

**분할 기준**: ① 변경 이유와 변경 주기가 다른 것은 분리한다 ② 운용 형상과 시험 형상은 분리한다 ③ 실행 환경이 다르면 분리한다.

**검토했으나 채택하지 않은 안**: 궤도 계산(Flight Dynamics)을 별도 CSCI로 두는 안. 실제 대형 지상국에서는 별도 서브시스템인 경우가 많지만, 이 프로젝트에서는 궤도 계산 결과의 유일한 소비자가 관제 소프트웨어 자신이고 규모도 작아 CSCI-1 내부의 CSC로 두었다.

| CSC-1.2 원격명령 | 명령 등록·취소·만료, 송신과 재전송, 도달·실행 확인 | `CommandDispatcher`, `CommandService`, `CommandRepository` |
| CSC-1.3 원격측정 | 수신·저장, 누락 식별, 한계치 비교, 재생 데이터 병합 | `TelemetryIngestService`, `TelemetryRepository` |

### 3.3 현재 구현과 설계의 차이 (알려진 항목)

CSCI-3은 **현재 CSCI-1과 같은 프로세스에서 실행**됩니다. 형상 분리 관점에서는 결함이며, 다음과 같이 관리하고 있습니다.

- CSCI 간에 주고받는 자료는 `com.gsc.protocol` 패키지의 프레임 정의로 **한정**되어 있고, 내부 구현을 직접 호출하지 않습니다.
- 운용 소프트웨어는 시뮬레이터를 `Uplink` 인터페이스로만 사용하므로, 실제 지상 장비 연동으로 교체할 수 있습니다.
- **향후 과제**: 별도 모듈·프로세스로 분리하고 인터페이스를 통신 규격으로 고정.

## 4. CSCI 간 인터페이스 (요약)

| 구간 | 방향 | 내용 |
|---|---|---|
| I/F-1 | CSCI-2 → CSCI-1 | REST: 명령 등록·취소, 배속·패스 이동, 채널 설정 |
| I/F-2 | CSCI-1 → CSCI-2 | WebSocket(STOMP): 추적 상태(4회/초), 상태 데이터, 명령 상태 변경, 운용 이벤트 |
| I/F-3 | CSCI-1 → CSCI-3 | 원격명령 프레임(바이트): 순번, 명령 코드, 인자, 끝에 CRC-16 |
| I/F-4 | CSCI-3 → CSCI-1 | 상태 데이터 프레임(바이트): 상태값, 프레임 카운터, 수신 확인(CLCW), 최근 실행 결과, 끝에 CRC-16 / 레코더 재생 묶음(무손실 가정) |

명령 종류와 운용 모드는 열거형 선언 순서와 무관하게 **고정 코드값**으로 싣습니다. 선언 순서가 바뀌어도
이미 쓰인 프레임 해석이 달라지지 않도록 하기 위한 것입니다.

## 5. 요구사항 추적표

| 시스템 요구사항 | 소프트웨어 요구사항 | 구현 (CSU) | 검증 (자동 시험) |
|---|---|---|---|
| SYS-01 | SRS-TRK-01 고도각이 마스크(5°)와 같아지는 시각을 AOS/LOS로 산출한다 | `OrbitService.predictPasses` | `predictedPassesStartAndEndAtTheElevationMask`, `passesAreOrderedAndDoNotOverlap` |
| SYS-01 | SRS-TRK-02 패스 진행 중 재예측해도 해당 패스의 AOS는 변하지 않는다 | `TrackingService.refreshPasses` | `passInProgressKeepsItsRealAos` |
| SYS-02 | SRS-TRK-03 교신 여부는 지상 소프트웨어에서만 판정한다 | `TrackingService.tick` | `issFliesInLowEarthOrbitWithinItsInclination` (궤도 기준값), 수동 확인 |
| SYS-03, SYS-04 | SRS-TC-01 교신 불가 시 송신하지 않고 대기시키며, 교신 시작 시 등록 순서대로 송신한다 | `CommandDispatcher.tick` | `outOfContactCommandsWaitAndGoOutInIssueOrderAtAos` |
| SYS-05 | SRS-TC-02 미확인 명령이 T1 내에 확인되지 않으면 순서대로 재전송한다 | `CommandDispatcher.tick` | `ackTimeoutRetransmitsEveryOutstandingFrameInOrder` |
| SYS-05 | SRS-TC-03 미확인 명령은 동시에 W개를 넘지 않는다 | `CommandDispatcher.tick` | `windowLimitsUnacknowledgedFrames` |
| SYS-05 | SRS-SIM-01 위성은 기대하는 번호의 명령만 수용하고 중복·순서 어긋남은 폐기한다 | `Farm.receive` | `acceptsOnlyTheExpectedFrame`, `retransmittedFrameIsDiscardedButStillAcknowledged`, `gapIsRejectedAndFlagsRetransmit` |
| SYS-05 | SRS-TC-04 유실이 있는 채널에서도 각 명령은 정확히 한 번, 순서대로 실행된다 | CSC-1.2 + CSC-3.2 | `lossyChannelStillDeliversEveryCommandExactlyOnceAndInOrder` (업링크 40%, 수신확인 30% 유실) |
| SYS-06 | SRS-TC-05 도달 확인(CLCW)과 실행 결과를 별도 상태로 관리하며, 늦게 도착한 확인이 앞선 상태를 되돌리지 않는다 | `CommandRepository.ackBelow`, `markExecuted` | `lateAcknowledgementNeverRollsBackAnExecutedCommand`, `rejectedExecutionIsReportedSeparatelyFromDelivery` |
| SYS-07 | SRS-TC-06 취소·만료된 명령은 송신하지 않으며 순번을 소모하지 않는다 | `CommandRepository.expire`, `cancel` | `expiredAndCancelledCommandsNeverConsumeASequenceNumber` |
| SYS-08 | SRS-TM-01 수신 프레임의 카운터 불연속을 누락으로 집계한다 | `TelemetryIngestService.onRealtimeFrame` | 수동 확인 (화면의 "TM 누락 감지") |
| SYS-09 | SRS-TM-02 교신 불가 구간의 저장 데이터를 다음 교신에서 수신해 이력에 병합한다 | `OnboardRecorder`, `TelemetryIngestService.onPlayback` | 수동 확인 (차트의 재생 구간) |
| SYS-10 | SRS-TM-03 고정 한계치 이탈 시 경보 이벤트를 생성한다 | `TelemetryIngestService.checkLimits` | 수동 확인 |
| SYS-11 | SRS-SIM-02 미션 시각은 배속·건너뛰기를 지원하되 과거로 이동하지 않는다 | `SimulationClock` | `runsAtConfiguredSpeed`, `changingSpeedDoesNotJumpTime`, `onlyMovesForward`, `speedZeroPauses` |
| SYS-12 | SRS-SYS-01 재시작 시 미션 시각이 저장된 이력보다 과거로 가지 않으며, 지상·위성의 명령 번호를 일치시킨다 | `SimulationBootstrap.synchronize` | `restartResumesMissionTimeAfterTheLatestStoredHistory` |
| SYS-13 | SRS-TC-07 원격명령 프레임에 CRC를 붙이고, 위성은 불일치 프레임을 응답 없이 폐기한다 | `Crc16Ccitt`, `TcFrameCodec`, `SpacecraftSimulator.receiveTc` | `TcFrameCodecTest.everySingleBitFlipIsDetected`, `Crc16CcittTest` |
| SYS-13 | SRS-TM-04 텔레메트리 프레임에 CRC를 붙이고, 지상은 불일치 프레임을 폐기해 누락으로 집계한다 | `TmFrameCodec`, `TelemetryIngestService.onRealtimeFrame(byte[])` | `TmFrameCodecTest.everySingleBitFlipIsDetected` |
| SYS-05 | SRS-TC-08 위성이 번호 공백을 보고하면 타이머 만료를 기다리지 않고 재전송한다 | `CommandService.onClcw`, `CommandDispatcher.onRetransmitRequested` | `survivesLongRandomisedFaultInjection` (보고 경로 포함) |
| SYS-14 | SRS-TC-09 재전송 한도 초과 시 송신을 중지하고 경보하며, 재개는 운용자가 한다 | `CommandDispatcher.tick`, `resume` | `FopSuspensionIT` 2건 |
| SYS-05 | SRS-SYS-02 유실·손상·연속 손실이 섞인 환경에서도 순서·1회 실행이 유지된다 | CSC-1.2 + CSC-3.2 | `survivesLongRandomisedFaultInjection` (유실 40%, 비트 오류 10%, 시드 8종) |

**검증 현황**: 자동 시험 31건이 위 항목을 확인하며, GitHub Actions에서 매 변경마다 실행됩니다.
"수동 확인" 항목은 자동 시험이 없는 부분으로, 남은 과제입니다.

**고장 주입 시험 결과**: 유실 40% · 비트 오류 10% · 교신 120초 / 두절 60초를 반복하는 환경에서
명령 30건을 시드 8종으로 반복 전달했을 때, 매번 1~30번이 순서대로 정확히 한 번씩 실행되고
마지막에 모두 수신 확인되었습니다(최악의 경우도 시뮬레이션 15분 이내).
실행 중 확인한 값으로는, 비트 오류를 주입한 프레임 수와 CRC로 폐기된 프레임 수가 양방향 모두 일치했습니다.

## 6. 주요 설계 파라미터와 근거

| 파라미터 | 현재 값 | 근거 |
|---|---|---|
| 최저 고도각(마스크) | 5° | 낮은 고도각에서는 지형 차폐와 대기 통과 거리 증가로 링크 품질이 나빠짐. 지형별 마스크는 미반영. |
| 전송 윈도우 W | 4 | 짧은 패스에서 왕복 대기 시간을 줄이되, 유실 시 재전송량이 과도해지지 않는 선. |
| 재전송 타이머 T1 | 3초 | **아래 설명 참조. 계산이 아닌 여유값이며, 빠른 재전송으로 보완함.** |
| 재전송 한도 | 12회 | 넘으면 송신 중지 + 운용자 경보. 한도는 재개 시점부터 다시 센다. |
| 레코더 기록 주기 | 60초 (미션 시각) | 장기 추세 확인에 충분한 해상도와 저장 용량의 절충. |
| 한계치 | 배터리 25%, 온도 −5~35°C | 고정 기준. 학습 모델이 아님. |
| 오류 검출 | CRC-16/CCITT | CCSDS 전송 프레임에서 쓰는 방식. 단일 비트 오류는 전부 검출됨을 시험으로 확인. |

### T1(재전송 타이머) 값에 대하여

현재 3초는 **시뮬레이터에서 응답이 올 수 있는 최악 시간의 약 2배**로 잡은 여유값입니다. CCSDS COP-1에서도 이 타이머는 표준 고정값이 아니라 임무별 운용 파라미터입니다.

응답 경로 (현재 시뮬레이션 기준)

```
업링크 전파 0.12초 + 위성의 다음 상태 프레임까지 최대 1.0초 + 다운링크 전파 0.12초 + 지상 송신 주기 0.2초 ≈ 1.44초
```

**문제**: Go-Back-N에서는 앞선 명령 하나가 유실되면 뒤 명령이 T1 동안 멈춥니다. 2분짜리 짧은 패스에서 3초는 교신 시간의 2.5%이며, 유실이 반복되면 누적 손실이 커집니다.

**대응 (적용 완료)**

위성은 기대하던 번호가 오지 않으면 CLCW에 **재전송 요청 플래그**를 세웁니다. 지상은 이 보고를 받으면
**타이머 만료를 기다리지 않고 즉시 재전송**합니다(TCP의 빠른 재전송과 같은 착상). 따라서 대부분의 유실은
T1을 다 기다리지 않고 복구되고, T1은 그 보고마저 유실된 경우의 최후 수단으로 남습니다.

**남은 과제**

1. T1 자체를 여유값이 아니라 측정된 왕복 시간에 근거해 산정 (실제 저궤도에서는 전파 왕복이 수~수십 ms이므로 수신 확인 보고 주기가 지배적).
2. 유실률과 T1을 바꿔 가며 "명령 N건 전달에 걸린 교신 시간"을 측정해 값의 타당성을 정량 확인.

## 7. 향후 과제

| 항목 | 내용 |
|---|---|
| 시뮬레이터 분리 | CSCI-3을 별도 모듈·프로세스로 분리하고 인터페이스를 규격으로 고정 |
| 프레임 형식 | 현재는 **자체 바이너리 형식 + CRC**. CCSDS Space Packet 규격(헤더 필드, APID 등)에 맞추는 것은 미적용 |
| T1 산정 | 측정 왕복 시간에 근거한 타이머 값 산정과 정량 확인 |
| 교신 중 유실 복구 | 교신 중 사라진 텔레메트리는 현재 **누락으로 집계만** 하고 복구하지 못한다. 복구하려면 레코더를 상시 기록하고 지상이 누락 구간을 재요청해야 하는데, **지상이 수신을 확인하기 전까지 레코더를 비울 수 없다**는 문제가 따라온다. 실제로는 CFDP 같은 파일 단위 전송 프로토콜이 이 역할을 한다 |
| 보안 | 명령 인증·암호화 없음. CRC는 자연적 오류만 검출하며 위조를 막지 못한다(보안은 별도 표준의 영역) |
| 대용량 임무 데이터 | X 밴드 관측 데이터 다운링크 계획(패스별 전송 가능량, 우선순위, 파일 단위 재전송)은 범위 밖. 별도 채널이지만 결국 같은 교신 시간을 나눠 쓰므로 계획 수립이 필요 |
| 자동 시험 확대 | 상태 데이터 누락 식별, 재생 병합, 한계치 경보의 자동 시험 |
| 정량 신뢰성 목표 | "명령 전달 성공률 99.x%" 같은 수치 요구사항과 장시간 연속 시험, 커버리지 측정 |
