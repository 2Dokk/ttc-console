# 인터페이스 정의서 (ICD)

이 시스템의 구성요소가 서로 주고받는 데이터의 **형식과 규칙**을 정의한다.
각 CSCI는 아래 정의만으로 통신하며, 상대의 내부 구현을 직접 호출하지 않는다.

| 식별자 | 구간 | 매체 | 방향 |
|---|---|---|---|
| **I/F-1** | 운용자 콘솔(CSCI-2) → 지상 관제 SW(CSCI-1) | HTTP/REST | 요청-응답 |
| **I/F-2** | 지상 관제 SW → 운용자 콘솔 | WebSocket(STOMP) | 서버 발행 |
| **I/F-3** | 지상 관제 SW → 위성(CSCI-3) | RF 업링크 (바이트 프레임) | 단방향 |
| **I/F-4** | 위성 → 지상 관제 SW | RF 다운링크 (바이트 프레임) | 단방향 |

> 바이트 순서는 **빅엔디안**, 문자열은 **UTF-8**, 시각은 **UTC epoch 밀리초**를 쓴다.
> 실수는 IEEE 754 단정밀도(float, 4바이트). 소수점 둘째 자리까지만 운용에 사용한다.

---

## 1. 공통 — 오류 검출 (CRC)

I/F-3, I/F-4의 모든 프레임은 **맨 뒤 2바이트에 CRC**를 붙인다.

| 항목 | 값 |
|---|---|
| 방식 | CRC-16/CCITT-FALSE |
| 생성 다항식 | `0x1021` |
| 초기값 | `0xFFFF` |
| 반전 | 없음 (입력·출력 모두) |
| 계산 범위 | 프레임의 **처음부터 CRC 직전까지** 전체 |
| 표준 검증값 | `"123456789"` → `0x29B1` |

**수신 측 규칙**: 다시 계산한 값이 실린 값과 다르면 **프레임 전체를 폐기**한다. 응답하지 않으며,
송신 측은 재전송 절차(I/F-3) 또는 프레임 카운터 불연속(I/F-4)으로 이를 알게 된다.

## 2. I/F-3 — 원격명령 프레임 (지상 → 위성)

| 오프셋 | 길이 | 필드 | 형식 | 설명 |
|---|---|---|---|---|
| 0 | 8 | 프레임 순번 N(S) | 부호 있는 정수 | 1부터 증가. 첫 송신 시 부여하며 재전송해도 바뀌지 않는다 |
| 8 | 1 | 명령 코드 | 부호 없는 정수 | 아래 표 참조 |
| 9 | 2 | 인자 길이 L | 부호 없는 정수 | 0 ~ 65535 |
| 11 | L | 인자 | UTF-8 JSON | 예: `{"mode":"MISSION"}`, 없으면 `{}` |
| 11+L | 2 | CRC-16 | — | 0 ~ (10+L) 바이트에 대해 계산 |

**명령 코드** (열거형 선언 순서와 무관하게 값 고정)

| 코드 | 명령 | 인자 | 비고 |
|---|---|---|---|
| 1 | PING | 없음 | 링크 점검 |
| 2 | SET_MODE | `{"mode":"NOMINAL"\|"MISSION"\|"SAFE"}` | 배터리 40% 미만이면 MISSION 거부 |
| 3 | HEATER | `{"on":true\|false}` | |
| 4 | PAYLOAD_POWER | `{"on":true\|false}` | MISSION 모드에서만 ON 가능 |

**수신 규칙 (위성)**
1. CRC 불일치 → 폐기
2. 순번 = V(R) → **수용**, V(R) 증가
3. 순번 < V(R) → 이미 받은 프레임, 폐기 (CLCW로 재확인)
4. 순번 > V(R) → 공백 발생, 폐기하고 **재전송 요청 플래그**를 세움

## 3. I/F-4 — 텔레메트리 프레임 (위성 → 지상)

교신 중 **1초 주기**로 전송한다.

| 오프셋 | 길이 | 필드 | 형식 | 단위·범위 |
|---|---|---|---|---|
| 0 | 8 | 프레임 카운터 | 정수 | 1부터 증가. 불연속 = 수신 누락 |
| 8 | 8 | 위성 시각 | 정수 | epoch ms (UTC) |
| 16 | 4 | 배터리 | float | % (0~100) |
| 20 | 4 | 온도 | float | °C |
| 24 | 4 | 자세 롤 | float | ° |
| 28 | 4 | 자세 피치 | float | ° |
| 32 | 4 | 자세 요 | float | ° |
| 36 | 1 | 운용 모드 | 정수 | 1=NOMINAL, 2=MISSION, 3=SAFE |
| 37 | 1 | 상태 비트 | 비트 필드 | bit0 히터, bit1 탑재체, bit2 일조 (1=ON) |
| 38 | 8 | CLCW V(R) | 정수 | 위성이 다음에 기대하는 명령 순번 |
| 46 | 1 | 재전송 요청 | 정수 | 1이면 번호 공백 발생 |
| 47 | 1 | 실행 보고 개수 N | 정수 | 0 ~ 8 |
| 48 | 가변 | 실행 보고 × N | 아래 표 | 최근 실행 결과를 반복 전송 |
| 끝 | 2 | CRC-16 | — | 앞의 모든 바이트에 대해 계산 |

**실행 보고 (1건, 19 + M 바이트)**

| 길이 | 필드 | 설명 |
|---|---|---|
| 8 | 명령 순번 | 어느 명령의 결과인지 |
| 1 | 성공 여부 | 1=실행 완료, 0=거부 |
| 8 | 실행 시각 | epoch ms |
| 2 | 메시지 길이 M | |
| M | 결과 메시지 | UTF-8. 예: `"탑재체는 MISSION 모드에서만 켤 수 있음"` |

**설계 의도**: 수신 확인(CLCW)과 실행 보고를 **매 프레임에 반복해서** 싣는다.
프레임 하나가 유실돼도 다음 프레임이 같은 정보를 다시 전달하므로, 확인이 영구히 사라지지 않는다.

### 3-1. 레코더 재생 (I/F-4 보조)

교신 불가 구간에 저장된 샘플을 교신 중 **초당 최대 60개**씩 내려보낸다.
`{ 샘플 목록, 최근 실행 보고, 남은 개수 }` 구조이며, **이 프로젝트에서는 무손실로 가정**한다
(실제로는 CFDP 같은 파일 단위 전송 절차가 필요 — 한계로 명시).

## 4. I/F-1 — 운용자 콘솔 → 지상 관제 SW (REST)

| 메서드·경로 | 요청 | 응답 |
|---|---|---|
| `GET /api/config` | — | 위성 정보(이름, NORAD, TLE 시각), 지상국 정보, FOP 설정 |
| `GET /api/state` | — | 미션 시각, 배속, 위성 위치, 방위/고도각, 교신 여부, 일조, 현재·다음 패스 |
| `GET /api/passes?count=n` | n ≤ 12 | 다가오는 패스 목록 (AOS, LOS, 최대 고도각 등) |
| `GET /api/passes/active/skytrack` | — | 현재(또는 다음) 패스의 방위·고도각 궤적 (10초 간격) |
| `GET /api/orbit/track` | behindMin, aheadMin, stepSec | 지상궤적 좌표 목록 |
| `POST /api/commands` | `{type, args, expiresInMinutes?}` | 등록된 명령 (201) |
| `GET /api/commands?limit=n` | n ≤ 500 | 명령 목록과 상태 |
| `POST /api/commands/{id}/cancel` | — | 취소된 명령. 대기 상태가 아니면 400 |
| `GET /api/telemetry?minutes=&limit=` | — | 저장된 텔레메트리 (실시간 + 재생) |
| `GET /api/events?limit=n` | n ≤ 300 | 운용 이벤트 로그 |
| `GET /api/link` | — | 채널 설정·통계, 수신 통계, FOP 상태 |
| `PUT /api/link` | `{uplinkLoss, downlinkLoss, bitErrorRate}` | 각 0~1. 범위 밖이면 400 |
| `POST /api/fop/resume` | — | 재전송 한도로 중지된 송신을 재개 |
| `POST /api/clock/speed` | `{speed}` | 0 ~ 1000 |
| `POST /api/clock/skip-to-next-pass` | — | 다음 AOS 60초 전으로 이동 |

**오류 응답**: `{"error": "사유"}` · 400 잘못된 요청 · 409 현재 상태에서 불가능

## 5. I/F-2 — 지상 관제 SW → 운용자 콘솔 (WebSocket)

접속: `/ws` (STOMP)

| 주제 | 주기·시점 | 내용 |
|---|---|---|
| `/topic/state` | 초당 4회 | 추적 상태 (`GET /api/state`와 동일 구조) |
| `/topic/telemetry` | 프레임 수신 시 | 실시간 텔레메트리 1건 |
| `/topic/telemetry/playback` | 재생 수신 시 | 재생 샘플 묶음 + 남은 개수 |
| `/topic/commands` | 상태 변경 시 | 변경된 명령 1건 |
| `/topic/events` | 발생 시 | 운용 이벤트 (시각, 등급, 분류, 메시지) |

## 6. 인터페이스 설계 원칙

1. **형식을 먼저 정하고 그 약속으로만 통신한다.** CSCI 간에 상대의 내부 구조를 직접 참조하지 않는다.
2. **식별값은 고정한다.** 명령 코드와 운용 모드 코드는 열거형 선언 순서가 바뀌어도 값이 변하지 않는다.
3. **손상은 검출해서 버린다.** 내용을 추측해 복구하지 않는다.
4. **중요한 상태는 반복해서 보낸다.** 수신 확인과 실행 보고는 매 프레임에 다시 실린다.
5. **시각은 두 종류를 구분한다.** 위성이 측정한 시각(`recordedAt`)과 지상이 받은 시각(`receivedAt`)을 따로 저장한다. 재생 데이터는 두 값이 수 시간 차이 날 수 있다.
